# CI: Jenkins and SonarQube on Docker Compose

The CI server for [`vigil`](https://github.com/ameurmasmoudi/vigil). A push to the app repo reaches Jenkins through a
GitHub webhook and runs the `Jenkinsfile` from that repo:

```
tests (api ∥ worker) ─▶ SonarQube + quality gate (api, then worker) ─▶ Trivy DB update
   ─▶ image build + Trivy scan (api ∥ worker) ─▶ push to GHCR (main only)
```

Branches run everything except the push. Images are published as `ghcr.io/ameurmasmoudi/vigil-{api,worker}:<commit sha>`.

## Services

| Service | Image | Role | Reachable at |
|---------|-------|------|--------------|
| `jenkins` | `jenkins/jenkins` LTS (JDK 25) | Controller: schedules builds, stores credentials, runs no builds | `127.0.0.1:5000` |
| `agent` | built from `agent/` | The only build executor: JDK 25, Docker CLI + buildx, Trivy | Compose network only |
| `dind` | `docker:dind` | Docker daemon for builds (images, Testcontainers), TLS only | Compose network only |
| `sonarqube` | SonarQube Community Build | Static analysis and quality gate | `127.0.0.1:9000` |
| `sonarqube-db` | `postgres:15-alpine` | SonarQube's database | Compose network only |
| `cloudflared` | `cloudflare/cloudflared` | Tunnel that exposes the GitHub webhook path, and nothing else | `vigil-ci.ameur.dev/github-webhook/` |

Volumes keep state between restarts: Jenkins home, SonarQube data and database, DinD's images and build cache,
the Maven repository (`maven_cache`) and Trivy's vulnerability databases (`trivy_db`, about 3 GB).

## Docker access: Docker-in-Docker over TLS

Builds need a real Docker daemon: Testcontainers starts PostgreSQL and Redis during the tests, and the pipeline builds
images. Options considered:

| Option | Why not |
|--------|---------|
| Mount the host's Docker socket | Builds could see, stop or replace every container and image on the host |
| Daemonless builders (Kaniko, BuildKit rootless) | Build images, but cannot run the containers Testcontainers needs |
| Docker access on the controller | The controller holds every credential and faces the tunnel; builds must not run there |

Chosen: a dedicated `dind` daemon that only the agent can reach, over TLS (`tcp://dind:2376`). The CA and client
certificates are generated by DinD into the `client_certs` volume; the agent mounts the client part read-only and
never sees the CA key. No DinD port is published on the host.

Accepted risk: DinD runs `privileged`, which is root-equivalent on the host. The mitigation is controlling which code
runs on the agent: pull requests from forks are not built, and only the webhook path is public. On a shared server
the boundary would be a throwaway VM per build.

The agent is a permanent inbound agent rather than one container per build: only it holds the DinD client
certificates, the controller needs no Docker access at all, and the Maven and Trivy caches stay warm.

## Security model

- The controller has **0 executors**; every build runs on the `docker-agent` node.
- Jenkins and SonarQube listen on `127.0.0.1` only. From the internet, the tunnel forwards exactly
  `^/github-webhook/$` to Jenkins and answers 404 for everything else (UI, login, script console).
- A Cloudflare WAF rule admits only GitHub's webhook IP ranges (`hooks` in `https://api.github.com/meta`) on the
  CI hostname.
- GitHub signs webhook deliveries with a shared secret; Jenkins rejects unsigned requests (HTTP 400).
- Credentials live in Jenkins' credential store and are used through credentials binding; the GHCR token is a classic
  token with `write:packages` only, logged in with `--password-stdin` and logged out after the push.
- Nothing secret is committed: `.env` and the tunnel credentials (`cloudflared/*.json`) are ignored.

## Running it

Prerequisites: Docker with Compose, `vm.max_map_count` of at least 262144 (SonarQube's Elasticsearch), and a
Cloudflare tunnel for the webhook.

```
cp .env.example .env     # fill in the values, see below
docker compose up -d --build
```

| Variable | Used by | Value |
|----------|---------|-------|
| `SONAR_DB_NAME`, `SONAR_DB_USER`, `SONAR_DB_PASSWORD` | `sonarqube`, `sonarqube-db` | Any values; set once, before the first start |
| `JENKINS_SECRET` | `agent` | Shown on the `docker-agent` node page in Jenkins once the node exists |

The tunnel needs its credentials file next to `cloudflared/config.yml`. To create a tunnel and route the hostname:

```
cloudflared tunnel create <name>
cloudflared tunnel --config cloudflared/config.yml route dns --overwrite-dns <name> <hostname>
cp ~/.cloudflared/<tunnel-id>.json cloudflared/ && chmod 444 cloudflared/<tunnel-id>.json
```

Pass `--config` explicitly: without it, `cloudflared` falls back to `~/.cloudflared/config.yml` and can act on a
different tunnel than the one named. The file is made world-readable because the container runs as uid 65532.

## Configuration done in the UIs

Jenkins and SonarQube are not configured as code yet, so a fresh volume needs these steps.

**Jenkins** (`http://localhost:5000`):

1. Built-in node: 0 executors. New permanent node `docker-agent` (label `docker-agent`, remote root
   `/home/jenkins/agent`, launched as an inbound agent); copy its secret into `JENKINS_SECRET` and recreate `agent`.
2. Plugins: Pipeline, GitHub Branch Source, Credentials Binding, SonarQube Scanner.
3. Credentials (global):

   | ID | Kind | Contents |
   |----|------|----------|
   | `github-vigil` | Username with password | GitHub user + fine-grained token with read-only contents (adding read and write commit statuses lets Jenkins show build results on GitHub) |
   | `github-webhook-secret` | Secret text | Shared secret of the GitHub webhook |
   | `sonarqube-secret` | Secret text | SonarQube token (a Global Analysis Token is the narrowest type that works) |
   | `ghcr-token` | Username with password | GitHub user + classic token with only `write:packages` |

4. System: GitHub server with `github-webhook-secret` as shared secret; SonarQube server named `sonarqube` at
   `http://sonarqube:9000` with `sonarqube-secret`. Leave the Jenkins URL at `http://localhost:5000/`.
5. Multibranch Pipeline job `vigil` on the app repo with `github-vigil`; fork pull requests: trust nobody.
   Optional: a periodic scan once a day as a fallback for missed webhooks.

**SonarQube** (`http://localhost:9000`):

1. Generate the token for `sonarqube-secret`.
2. Disable local webhook validation (Administration → General → Security): the webhook targets a private address.
3. Webhook `http://jenkins:8080/sonarqube-webhook/` so `waitForQualityGate` gets the result pushed.

**GitHub** (app repo → Settings → Webhooks): payload URL `https://<hostname>/github-webhook/`, content type JSON,
the shared secret, push events.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Testcontainers can't pull images, `server misbehaving` on DNS | The host's Docker sends container DNS to `172.17.0.1`; DinD's own bridge took the same address | `dind` runs with `--bip` and `--default-address-pool` on unused `10.x` ranges |
| `waitForQualityGate` hangs until the timeout | SonarQube can't reach Jenkins (inside the network Jenkins is `jenkins:8080`, not `5000`) | Fix the SonarQube webhook URL |
| A quality gate reports the other service's analysis | The plugin takes the build's last analysis and finds every `report-task.txt` below the current folder | Analyses run one after the other, each inside `dir(<service>)` |
| Trivy: `cache may be in use by another process` | Parallel scans share Trivy's on-disk scan cache | DB updated once per build; scans use `--skip-db-update --skip-java-db-update --cache-backend memory` |
| Trivy: `context deadline exceeded` | The Java DB (~1 GB) downloads inside the 5-minute scan timeout | DB download step with `--timeout 15m` before the scans |
| Webhook delivery returns an empty 404 from Cloudflare | The hostname's DNS record points to another tunnel | Re-route it with `route dns --overwrite-dns` and an explicit `--config` |
